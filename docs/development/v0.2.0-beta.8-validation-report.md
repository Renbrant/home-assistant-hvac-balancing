# v0.2.0-beta.8 Development and Validation Report

Status: APPROVED TO ADVANCE

Parent issue: #12 - v0.2.0: Migrate HVAC Balancing to a Home Assistant Custom Integration

---

## 1. Purpose of this development stage

The beta.8 stage moved HVAC Balancing from a development controller and virtual observation environment into a configurable Home Assistant Custom Integration capable of active control.

The objective was not merely to reproduce calculations.

The objective was to validate the complete path from Home Assistant inputs to Python controller decisions and finally to actuator commands, while keeping all active testing isolated inside the virtual HA Dev Test Bench.

The production Home Assistant system was not modified during beta.8 validation.

---

## 2. Architecture achieved

HVAC Balancing is now implemented as a Home Assistant Custom Integration under:

custom_components/hvac_balancing

The controller logic is separated from Home Assistant entity plumbing and actuator logic.

The integration currently contains distinct responsibilities for:

- controller calculations;
- Adaptive I policy;
- observation runtime;
- actuator runtime;
- configuration management;
- config flow;
- options flow;
- diagnostic sensors;
- binary sensors;
- dynamic zone configuration.

The Python controller is no longer architecturally tied to Bed 1, Bed 2, or Bed 3.

---

## 3. Installation-agnostic configuration

Production configuration is now performed through the Home Assistant integration UI.

The user can select:

- central thermostat;
- reference temperature sensor;
- balancing zones;
- zone names;
- zone temperature sensors;
- zone booster fans;
- Central Assist strategy;
- Central Assist entity or climate behavior.

Balancing zones can be added, edited, renamed, and removed without changing Python source code.

Each zone has a stable internal identity so configuration changes do not unnecessarily destroy diagnostic identity.

The integration also cleans obsolete production diagnostic entities when zones are removed or changed.

---

## 4. Dynamic balancing zones

The original bedroom-specific architecture has been replaced by a zone-oriented architecture.

A configured zone contains the information required by the controller and actuator, including:

- stable zone ID;
- display name;
- temperature sensor;
- booster fan.

This means the same integration can eventually support installations containing bedrooms, offices, basements, living rooms, or other independently balanced spaces.

---

## 5. Production Active runtime

A dedicated active production runtime was introduced.

The integration distinguishes between:

- Test Bench / observation behavior;
- Production Active behavior.

Physical actuation requires an explicitly configured production runtime.

The actuator layer is isolated from the controller calculation engine so control decisions remain independently testable.

---

## 6. Active booster control

The Python actuator converts controller speeds from 0 through 10 into Home Assistant fan percentages from 0 through 100 percent.

The validated booster command sequence preserves the behavior required by the current Xtend/Tuya hardware:

1. set preset mode to FAN;
2. set requested percentage;
3. turn the fan on.

A controller demand of zero turns the configured booster fan off.

Physical service calls are isolated inside the actuator implementation.

---

## 7. Serialized actuator commands

Actuator updates are serialized.

A new controller update does not cancel a physical command sequence that is already in progress.

Instead, intermediate controller changes are coalesced and the newest snapshot is applied after the current command sequence completes.

This avoids partially executed fan sequences caused by rapid Home Assistant state changes.

---

## 8. Booster state reconciliation

The actuator no longer trusts device feedback as the only source of truth.

The runtime tracks successful commands while also inspecting current Home Assistant entity state.

Startup and watchdog events force reconciliation.

This protects against situations such as:

- stale Tuya state feedback;
- external state changes;
- temporary communication failures;
- device drift;
- missed commands;
- Home Assistant state inconsistencies.

---

## 9. Configurable Central Assist

Central HVAC airflow assistance is now installation-agnostic.

Supported Central Assist strategies include:

- direct fan entity;
- climate fan mode;
- Nest fan timer;
- disabled Central Assist.

This removes the previous architectural dependency on one specific Nest implementation.

One important implementation milestone was:

4825a2d - feat: make central assist configurable

---

## 10. Central Assist ownership

HVAC Balancing distinguishes between Central Assist that it started itself and circulation that may have been started externally.

The integration must not turn off circulation that belongs to:

- the user;
- another automation;
- another integration.

Only Central Assist owned by HVAC Balancing is eligible for automatic release.

---

## 11. Central Assist state-drift reconciliation

During Test Bench validation the Central Blower was intentionally forced OFF while the Python controller continued requesting Central Assist.

This exposed a real runtime issue.

The actuator originally trusted its in-memory ownership state and could assume that Central Assist remained active.

The behavior was corrected so the actuator verifies the actual Home Assistant state.

Relevant fix:

cf5d4f6 - fix: reconcile central assist state drift

Validated result:

- controller continued requesting Central Assist;
- virtual blower was externally turned OFF;
- actuator detected the mismatch;
- actuator automatically restored the blower to ON.

---

## 12. Five-minute Central Assist release grace

Central Assist release behavior was validated.

Observed sequence:

1. Severe Upstairs Heat created high airflow demand.
2. Central Assist Requested became ON.
3. Central Blower became ON.
4. Balanced House removed the demand.
5. Central Assist Requested immediately became OFF.
6. Central Blower remained ON.
7. Approximately five minutes later the Central Blower turned OFF automatically.

This confirms the intended delayed release behavior.

---

## 13. Persistent Central Assist ownership

Central Assist ownership is now stored through the Home Assistant storage API.

Ownership storage is tied to the exact configured adapter identity.

Stored state includes:

- whether HVAC Balancing owns Central Assist;
- the adapter fingerprint associated with that ownership.

Ownership is restored only when the persisted adapter matches the current configuration.

An already-active manual or external fan is not automatically claimed.

A successful release clears the persisted ownership state.

Relevant fix:

29c8bf2 - fix: persist central assist ownership across restart

---

## 14. Adaptive Episode architecture

Adaptive I no longer depends on a simple global wall-clock evaluation interval.

The controller measures effective cooling exposure independently for each zone.

Current evaluation windows are:

- error above 1.3 F and below 2.0 F: 20 cooling minutes;
- error from 2.0 F to below 3.0 F: 15 cooling minutes;
- error of 3.0 F or greater: 10 cooling minutes.

Idle compressor time is excluded.

Each balancing zone owns its own Adaptive Episode and deadline.

---

## 15. Adaptive I decision policy

Temperature improvement is normalized to degrees Fahrenheit per 10 minutes of actual cooling exposure.

Current policy:

- improvement below 0.10 F per 10 cooling minutes: increase Adaptive I;
- improvement from 0.10 to below 0.25 F per 10 cooling minutes: hold;
- improvement of at least 0.25 F per 10 cooling minutes: reduce Adaptive I.

Adaptive boost remains bounded by available proportional headroom.

## 16. Adaptive I active-runtime validation

The Adaptive I Persistent Error scenario was tested using the Production Active runtime mapped exclusively to virtual Test Bench entities.

Initial Bed 2 state:

- Base P = 8;
- Adaptive I = 0;
- PI Target = 8;
- Effective = 80 percent;
- Booster speed = 8.

After 10 minutes of actual cooling exposure:

- controller event became adaptive_due;
- Adaptive I changed from 0 to 1;
- PI Target changed from 8 to 9;
- Effective output changed from 80 to 90 percent;
- Bed 2 booster changed from speed 8 to speed 9;
- Adaptive Action became increase;
- a new Adaptive Episode started automatically.

This validated the complete control path from thermal error to physical actuator command.

## 17. Cooling to Idle to Cooling validation

Normal compressor cycling was explicitly tested.

Observed Bed 2 cooling exposure:

- Cooling: 03:08 / 10:00
- Idle: 03:08 / 10:00
- Cooling resumed: 03:08 / 10:00
- Later during Cooling: 03:35 / 10:00

Results:

- Cooling to Idle did not reset Adaptive I;
- Cooling to Idle did not reset the episode;
- Idle time was not counted;
- the Adaptive deadline was paused;
- returning to Cooling resumed from the previous exposure;
- Base P, Adaptive I, and PI target were preserved.

This confirms the intended fix for normal HVAC action transitions.

---

## 18. Hysteresis validation

Reference temperature during the guided test was 75.0 F.

Observed Bed 2 sequence:

- 76.4 F, error +1.4 F, rising: Base P 0 - PASS
- 76.5 F, error +1.5 F, rising: Base P 2 - PASS
- 76.6 F, error +1.6 F: Base P 2 - PASS
- 76.4 F, error +1.4 F, falling: Base P 2 - PASS
- 76.3 F, error +1.3 F, falling: Base P 0 - PASS

The first proportional stage therefore activates at the 1.5 F rising threshold but does not release until the falling threshold reaches 1.3 F.

## 22. Test Bench actuator reset separation

Core Test Scenarios originally reset both zone boosters and the Central Blower.

That behavior interfered with Central Assist lifecycle testing.

The Test Bench was changed so normal scenario preparation resets only the three zone boosters.

A separate explicit fault/drift action was added:

HVAC Test - Force Reset All Actuators

Relevant commit:

4fc26e7 - test(dev): separate central assist from scenario reset

This allows scenario setup and Central Assist fault injection to be tested independently.

---

## 23. Restart behavior

A normal Home Assistant restart intentionally invokes the integration fail-safe shutdown path.

Controlled outputs are therefore shut down during graceful unload.

Expected production sequence is:

1. Home Assistant begins shutdown.
2. HVAC Balancing safely stops controlled outputs.
3. Home Assistant starts again.
4. Real physical sensors republish their actual values.
5. Python recalculates current demand.
6. Required actuators are commanded again.

The design intentionally avoids leaving booster fans blindly running while Home Assistant is unavailable.

---

## 24. Known non-blocking Test Bench limitation

The current virtual Test Bench uses YAML initial values for several environmental helpers.

Because of this, a simulated scenario such as Severe Upstairs Heat does not persist through a Home Assistant restart.

During restart testing the virtual temperature helpers returned to their default values and the controller correctly recalculated zero demand.

This is a Test Bench simulation limitation, not a Python controller failure.

Deferred improvement:

- allow the Test Bench environmental input helpers to restore previous values across restart;
- repeat restart-under-load validation with preserved virtual thermal conditions.

This item is explicitly considered non-blocking for beta.8 approval.

## 28. Next stage: controlled production cutover

The next stage will move the Python Custom Integration to the real Home Assistant installation.

The planned transition is:

- v0.1.3 calculation entities remain temporarily active for historical comparison;
- v0.1.3 physical actuator automation is disabled at cutover;
- v0.2 Python becomes the only authority commanding physical boosters and Central Assist.

Planned cutover sequence:

1. back up the production Home Assistant configuration;
2. deploy the Custom Integration files;
3. do not activate physical control until configuration is verified;
4. configure the real thermostat;
5. configure the real reference temperature sensor;
6. configure the real balancing zones;
7. configure the real booster fans;
8. configure the real Central Assist adapter;
9. verify every selected entity before actuation;
10. disable the legacy v0.1.3 physical actuator automation;
11. enable Python Production Active control;
12. retain legacy calculation sensors for comparison;
13. monitor real room response and Python diagnostics;
14. preserve v0.1.3 as rollback/reference during the observation period.

No production cutover was performed during beta.8 development validation.
