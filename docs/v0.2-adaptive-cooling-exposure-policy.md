# HVAC Balancing v0.2 - Adaptive Cooling Exposure Policy

## Status

Core integration candidate for the post-parity Adaptive I controller.

`controller.py` now supports the cooling-exposure policy behind an explicit
strategy setting. The validated `legacy_wall_clock` strategy remains the
default until live Test Bench comparison is complete.

The new strategy is therefore testable without silently replacing the known
beta.3 baseline.

## Problem with the fixed wall-clock window

The current Adaptive I algorithm evaluates performance after a fixed 20-minute
wall-clock window.

Wall-clock time is not equivalent to thermal opportunity.

Examples:

- 20 minutes cooling + 0 minutes idle = 20 minutes useful cooling exposure.
- 10 minutes cooling + 10 minutes idle = only 10 minutes useful exposure.
- 2 minutes cooling + 18 minutes idle = very little useful evidence.

The next controller should therefore accumulate actual HVAC cooling exposure
instead of assuming every elapsed minute represents useful cooling.

## Decision cadence

The Home Assistant adapter may continue producing an Adaptive Tick every
5 minutes.

A tick means:

"Check whether enough evidence exists to make an Adaptive decision."

A tick does not mean:

"Always change Adaptive I."

## Variable cooling-exposure requirement

Required effective cooling exposure depends on current directional error.

| Directional error | Required effective cooling |
|---|---:|
| <= 1.3 F | Reset |
| > 1.3 F and < 2.0 F | 20 minutes |
| >= 2.0 F and < 3.0 F | 15 minutes |
| >= 3.0 F | 10 minutes |

This provides faster response to severe imbalance without making small errors
overly reactive.

## Improvement normalization

The old algorithm used absolute improvement thresholds over a fixed 20-minute
window:

- less than 0.2 F improvement: increase Adaptive I
- 0.2 F through less than 0.5 F: hold
- at least 0.5 F: decrease Adaptive I

With variable windows, raw absolute improvement is not comparable.

Improvement is therefore normalized to:

F of error improvement per 10 minutes of effective cooling.

Equivalent normalized thresholds:

| Improvement rate | Adaptive action |
|---|---|
| < 0.10 F / 10 cooling min | Increase +1 |
| >= 0.10 and < 0.25 F / 10 cooling min | Hold |
| >= 0.25 F / 10 cooling min | Decrease -1 |

A negative improvement rate means the imbalance is becoming worse and therefore
falls in the Increase category.

## Reset and unwind

- error <= 1.3 F: reset Adaptive I and observation history
- error > 1.3 F and < 1.5 F: after sufficient cooling exposure, unwind by one
- Base P hysteresis remains independent from this policy
- PI Target remains capped at Speed 10
- Adaptive I changes by at most one step per eligible evaluation

## Cooling exposure

Future integration into controller.py will accumulate cooling exposure only
while the previous observed HVAC condition was:

- hvac_mode == cool
- hvac_action == cooling

Idle periods pause the exposure accumulator.

The sequence:

cooling -> idle -> cooling

must therefore preserve accumulated exposure while excluding the idle duration.

## Safety

The new policy must preserve:

- no controller actuation inside the pure Python module
- no Home Assistant imports
- invalid-temperature fail-safe behavior
- per-zone state independence
- Base P hysteresis
- Speed 10 anti-windup
- Central Assist threshold behavior
- observation-only validation before actuation

## Planned diagnostics

The observation adapter should eventually expose, per zone:

- current directional error
- accumulated cooling exposure
- required cooling exposure
- exposure progress
- reference error
- improvement rate in F / 10 cooling min
- selected Adaptive action
- Adaptive I
- PI Target

This will make each Adaptive decision explainable from the Test Bench.
