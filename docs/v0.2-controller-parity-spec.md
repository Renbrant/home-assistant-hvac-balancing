# HVAC Balancing v0.2 Controller Parity Specification

## Status

This document defines the behavioral contract for the first Python controller
implemented during the v0.2.0 migration.

Reference implementation:

```text
v0.1.3 — Cooling-Only PI-Lite Balancing
```

Primary source files:

```text
HomeAssistant/templates.yaml
HomeAssistant/automation.yaml
```

The initial Python controller must reproduce this behavior before new control
strategies or tuning changes are introduced.

The governing principle is:

> Functional parity first. Enhancements second.

---

# 1. Controller scope

The v0.1.3 controller balances rooms only while the thermostat HVAC mode is:

```text
cool
```

No bedroom balancing demand is generated for:

```text
heat
heat_cool
off
unknown
unavailable
other unsupported modes
```

Heating balancing is explicitly deferred.

The Python parity implementation must therefore remain cooling-only.

---

# 2. Independent temperature concepts

The physical system contains three different temperature concepts.

## Thermostat measured temperature

This is the temperature measured internally by the central thermostat.

It influences the thermostat's own HVAC operation, including whether
`hvac_action` becomes:

```text
cooling
idle
```

It is not directly used to calculate bedroom balancing error in v0.1.3.

## Kitchen reference temperature

The balancing controller uses the independent Kitchen temperature sensor as the
thermal reference.

Current production entity:

```text
sensor.kitchen_temp_temperature
```

Virtual Test Bench equivalent:

```text
sensor.hvac_test_kitchen_temperature
```

## Room temperature

Each balancing zone has its own temperature sensor.

The controller compares this temperature against the Kitchen reference.

## Thermostat setpoint

The thermostat setpoint controls the central HVAC system.

The setpoint is not part of the current Base P or Adaptive I formula.

---

# 3. Raw temperature delta

For diagnostics:

```text
raw_delta = room_temperature - reference_temperature
```

The current YAML diagnostic delta sensor reports this rounded to one decimal
place.

Example:

```text
Room      = 77.18°F
Reference = 75.03°F

Raw difference       = 2.15°F
Diagnostic delta     = 2.2°F
```

Important:

The rounded diagnostic delta is NOT the input to the Base P controller.

Base P calculates directly from the source room and reference temperatures.

The Python core must preserve that distinction.

---

# 4. Cooling directional error

When HVAC mode is `cool`:

```text
error = room_temperature - reference_temperature
```

A positive error means the room is warmer than the Kitchen reference and may
require additional airflow.

Outside `cool`:

```text
error = 0
```

for controller-demand purposes.

If either temperature input is invalid or unavailable, the directional
calculation is invalid and the zone must fail safely.

---

# 5. Base P proportional controller

Each zone maintains an independent previous Base P target.

Valid speeds are:

```text
0
2
4
6
8
10
```

## Rising-demand curve

```text
error < 1.5°F        -> 0
1.5 <= error < 2.0   -> 2
2.0 <= error < 2.5   -> 4
2.5 <= error < 3.0   -> 6
3.0 <= error < 3.5   -> 8
error >= 3.5         -> 10
```

Equivalent function:

```text
rising(error):
    < 1.5  -> 0
    < 2.0  -> 2
    < 2.5  -> 4
    < 3.0  -> 6
    < 3.5  -> 8
    else   -> 10
```

---

# 6. Base P falling curve / hysteresis

The decreasing-demand thresholds are shifted downward by 0.2°F.

```text
error <= 1.3         -> 0
error <= 1.8         -> 2
error <= 2.3         -> 4
error <= 2.8         -> 6
error <= 3.3         -> 8
error >  3.3         -> 10
```

Equivalent function:

```text
falling(error):
    <= 1.3 -> 0
    <= 1.8 -> 2
    <= 2.3 -> 4
    <= 2.8 -> 6
    <= 3.3 -> 8
    else   -> 10
```

---

# 7. Base P hysteresis selection

Given:

```text
previous = previous Base P target
rising   = rising curve result
falling  = falling curve result
```

the v0.1.3 selection rule is:

```text
if rising > previous:
    base_target = rising

elif rising < previous:
    base_target = falling

else:
    base_target = previous
```

This exact rule must be preserved.

Example:

```text
previous = 4
error    = 1.9°F
rising   = 2
falling  = 4

result   = 4
```

The controller does not fall from Speed 4 to Speed 2 until error reaches
1.8°F or lower.

---

# 8. Base P unavailable-input behavior

If either:

```text
room temperature
reference temperature
```

cannot be converted to a numeric temperature, the current Base P template
reports no valid target.

The Python controller should represent this condition explicitly rather than
silently inventing a temperature.

Downstream effective demand must fail safely to zero.

---

# 9. Adaptive I / PI-lite state

Each zone independently maintains:

```text
adaptive_boost
reference_error
last_evaluation
```

Additional derived information includes:

```text
base_speed
directional_error
control_direction
headroom
```

No state is shared between zones.

---

# 10. Adaptive trigger model

The v0.1.3 Adaptive I calculation is triggered by:

```text
1. adaptive_tick
   every 5 minutes

2. hvac_mode_change
   actual climate entity STATE change

3. startup
   Home Assistant startup
```

The controller does NOT treat normal thermostat attribute updates as HVAC mode
changes.

In particular:

```text
cooling -> idle -> cooling
```

while the thermostat state remains:

```text
cool
```

must NOT reset:

```text
adaptive_boost
reference_error
last_evaluation
```

This behavior is a mandatory regression test for the v0.2 Python controller.

---

# 11. v0.1.3 Adaptive-I reset fix

The corrective v0.1.3 change modified the thermostat state trigger so that
attribute-only climate updates no longer cause a mode-change reset.

The semantic contract for Python is therefore:

```text
previous HVAC MODE != current HVAC MODE
    -> true mode-change event

previous HVAC MODE == current HVAC MODE
but hvac_action changed
    -> NOT a mode-change event
```

Examples:

```text
cool / cooling
    ->
cool / idle

NO RESET
```

```text
cool / idle
    ->
cool / cooling

NO RESET
```

```text
cool
    ->
off

MODE CHANGE
```

```text
off
    ->
cool

MODE CHANGE
```

---

# 12. Adaptive control direction

Current physical topology supports:

```text
mode == cool
    -> control_direction = cooling
```

All other modes:

```text
control_direction = none
```

When direction is `cooling`:

```text
error = room - reference
```

No reverse/heating calculation should be implemented in the parity controller.

---

# 13. Adaptive headroom / anti-windup

Adaptive I cannot cause the final target to exceed Speed 10.

When the Adaptive I state machine itself executes:

```text
headroom = max(10 - base_target, 0)
```

The stored adaptive value is then clamped:

```text
current = min(previous_boost, headroom)
current = max(current, 0)
```

Therefore, after an Adaptive I evaluation:

```text
0 <= adaptive_boost <= 10 - base_target
```

Important trigger-semantics detail:

A normal temperature or `hvac_action` update is not an Adaptive I trigger in
v0.1.3.

For example:

```text
previous Base P       = 4
stored Adaptive I     = 4

temperature changes
new Base P            = 8
NORMAL_UPDATE
```

At that instant the stored Adaptive I remains:

```text
4
```

while the final PI target is still safely capped:

```text
min(8 + 4, 10) = 10
```

At the next Adaptive I event, headroom becomes:

```text
10 - 8 = 2
```

and the stored Adaptive I is clamped to:

```text
2
```

This distinction is required for exact v0.1.3 trigger parity.

---

# 14. Adaptive evaluation interval

Adaptive calculation wakes approximately every 5 minutes, but performance is
evaluated only when:

```text
now - last_evaluation >= 1200 seconds
```

That is:

```text
20 minutes
```

If `last_evaluation` does not exist:

```text
due = false
```

The first eligible adaptive event initializes the observation window instead of
immediately adding integral correction.

---

# 15. Adaptive reset timing

The v0.1.3 Adaptive I entity is trigger-based.

Its state machine executes on:

```text
ADAPTIVE_TICK
HVAC_MODE_CHANGE
STARTUP
```

During such an Adaptive evaluation, boost becomes zero when:

```text
temperature input invalid
HVAC mode unsupported
true HVAC mode change
Base P >= 10
directional error <= 1.3
```

A plain temperature update does not itself execute the Adaptive I state
machine.

Therefore an ordinary `NORMAL_UPDATE` preserves:

```text
adaptive_boost
reference_error
last_evaluation
```

until the next Adaptive trigger.

The v0.2 controller adds one deliberate safety rule outside legacy parity:

> Invalid temperature input must expose zero PI demand and zero effective
> actuator demand immediately, even if stored Adaptive I state is preserved
> internally until the next Adaptive tick.

This safety override prevents an unavailable sensor from commanding equipment
during the interval before the next five-minute Adaptive evaluation.

---

# 16. Balanced threshold

When the Adaptive I state machine evaluates and:

```text
error <= 1.3
```

the zone is considered sufficiently balanced for Adaptive I purposes.

The Adaptive state becomes:

```text
adaptive_boost  = 0
reference_error = None
last_evaluation = None
```

Because the legacy Adaptive entity wakes every five minutes, a temperature
crossing below 1.3°F between ticks does not mutate its stored Adaptive state
until the next Adaptive event.

Base P still reacts immediately to the temperature change.

A future Adaptive demand starts with a fresh observation window after the reset.

---

# 17. Near-threshold unwind behavior

There is an important distinction between:

```text
error <= 1.3
```

and:

```text
1.3 < error < 1.5
```

When an Adaptive I event executes with:

```text
error <= 1.3
```

Adaptive state resets to zero and observation history is cleared.

For:

```text
1.3 < error < 1.5
```

Adaptive I is reduced by one step only when the 20-minute evaluation is due:

```text
adaptive_boost = max(current - 1, 0)
```

If the evaluation is not yet due, Adaptive I holds its current value.

A `NORMAL_UPDATE` does not perform either Adaptive operation; it preserves the
stored Adaptive state until the next Adaptive event.

---

# 18. Adaptive performance measurement

At the beginning of an observation window:

```text
reference_error = current directional error
```

The current YAML stores `reference_error` rounded to two decimal places.

At the end of an eligible observation window:

```text
improvement = reference_error - current_error
```

The Python parity implementation should preserve the two-decimal reference
sample semantics so parity tests remain deterministic.

---

# 19. Adaptive response curve

When an evaluation is due and the error remains at least 1.5°F:

## Poor improvement

```text
improvement < 0.2°F
```

Result:

```text
adaptive_boost = min(current + 1, headroom)
```

## Good improvement

```text
improvement >= 0.5°F
```

Result:

```text
adaptive_boost = max(current - 1, 0)
```

## Moderate improvement

```text
0.2 <= improvement < 0.5°F
```

Result:

```text
adaptive_boost = current
```

---

# 20. Reference-error sampling

These sampling rules apply when the Adaptive I state machine executes.

`NORMAL_UPDATE` preserves `reference_error` unchanged.

When valid COOL demand exists and:

```text
reference_error is absent
```

the current directional error becomes the new reference sample.

On a true HVAC mode change into COOL:

```text
reference_error = round(current_error, 2)
```

When 20 minutes have elapsed:

```text
reference_error = round(current_error, 2)
```

Otherwise:

```text
reference_error remains unchanged
```

---

# 21. Last-evaluation sampling

These timestamp rules apply when the Adaptive I state machine executes.

`NORMAL_UPDATE` preserves `last_evaluation` unchanged.

When valid COOL demand exists and no evaluation timestamp exists:

```text
last_evaluation = now
```

On a true HVAC mode change into COOL:

```text
last_evaluation = now
```

When at least 1200 seconds have elapsed:

```text
last_evaluation = now
```

Otherwise:

```text
last_evaluation remains unchanged
```

---

# 22. Important ordering of Adaptive I rules

The parity controller must distinguish ordinary updates from actual Adaptive
events.

Conceptually:

```text
calculate Base P from current temperatures

if event == NORMAL_UPDATE:
    preserve stored Adaptive I
    preserve reference_error
    preserve last_evaluation

else:
    execute Adaptive I state machine

    if invalid temperatures or unsupported mode:
        adaptive = 0
        clear observation history

    else:
        calculate error
        calculate headroom
        clamp previous adaptive to headroom

        if true_mode_change:
            adaptive = 0

        elif base >= 10:
            adaptive = 0

        elif error <= 1.3:
            adaptive = 0

        elif evaluation_not_due:
            adaptive = current

        elif error < 1.5:
            adaptive = max(current - 1, 0)

        elif reference_error is None:
            adaptive = current

        else:
            improvement = reference_error - error

            if improvement < 0.2:
                adaptive = min(current + 1, headroom)

            elif improvement >= 0.5:
                adaptive = max(current - 1, 0)

            else:
                adaptive = current
```

Regardless of stored Adaptive state:

```text
invalid temperature -> exposed PI target = 0
invalid temperature -> effective command = 0
```

That final rule is an intentional v0.2 fail-safe improvement.

---

# 23. Final PI target

For each valid zone:

```text
PI Target = Base P + Adaptive I
```

Limited to:

```text
PI Target <= 10
```

Equivalent:

```text
pi_target = min(base_target + adaptive_boost, 10)
```

---

# 24. Effective booster target

The effective target adds the compressor-active minimum-speed rule.

If HVAC mode is not `cool`:

```text
effective_speed = 0
```

If HVAC mode is `cool` and:

```text
hvac_action == cooling
```

then:

```text
effective_speed = max(pi_target, 1)
```

Otherwise, while the thermostat remains in COOL:

```text
effective_speed = pi_target
```

Effective percentage:

```text
effective_percentage = effective_speed * 10
```

Examples:

```text
mode        = cool
hvac_action = cooling
pi_target   = 0

effective_speed      = 1
effective_percentage = 10%
```

```text
mode        = cool
hvac_action = idle
pi_target   = 4

effective_speed      = 4
effective_percentage = 40%
```

```text
mode        = heat
pi_target   = 8

effective_speed      = 0
effective_percentage = 0%
```

---

# 25. Central blower assist decision

Central blower assistance is second-stage control.

A blower-assist request exists when:

```text
HVAC mode == cool
```

and at least one zone has:

```text
PI Target >= 8
```

Conceptually:

```text
central_assist_required =
    mode == "cool"
    and max(zone.pi_target) >= 8
```

The existing automation implements physical Nest behavior separately:

```text
request assist -> nest.set_fan_timer for 12 hours
release path   -> wait 5 minutes and verify demand remains below threshold
```

Those Home Assistant service-call mechanics belong to the later actuation layer,
not the pure Phase 2 calculation engine.

The pure controller should initially expose only the decision:

```text
central_assist_required: bool
```

---

# 26. Zone independence

The Python controller must not know about:

```text
Bed 1
Bed 2
Bed 3
```

as hard-coded controller logic.

Each zone receives equivalent inputs:

```text
zone temperature
reference temperature
previous zone state
HVAC mode
HVAC action
evaluation event
current time
controller settings
```

and returns an independent decision/state.

The integration may run any number of configured zones.

---

# 27. Pure controller boundary

Phase 2 should contain no Home Assistant service calls.

The controller calculation layer should not:

```text
fan.turn_on
fan.turn_off
fan.set_percentage
fan.set_preset_mode
nest.set_fan_timer
climate.set_fan_mode
```

Instead it returns a decision.

Suggested conceptual output:

```text
ZoneDecision
├── temperature_delta
├── directional_error
├── base_target
├── adaptive_boost
├── pi_target
├── effective_speed
├── effective_percentage
├── reference_error
├── last_evaluation
├── control_direction
├── balancing_active
└── reason
```

Integration-level output can derive:

```text
central_assist_required
```

from all zone decisions.

---

# 28. Event semantics for Python

The pure controller receives an explicit event reason instead of inferring
Adaptive resets from arbitrary Home Assistant updates.

Events:

```text
NORMAL_UPDATE
ADAPTIVE_TICK
HVAC_MODE_CHANGE
STARTUP
```

Semantics:

```text
NORMAL_UPDATE
    recalculate current proportional/effective decision
    preserve stored Adaptive I state
    preserve Adaptive observation window

ADAPTIVE_TICK
    execute Adaptive I state machine

HVAC_MODE_CHANGE
    execute true mode-change reset/start semantics

STARTUP
    execute startup Adaptive semantics
```

A later Home Assistant adapter translates entity changes into these events.

Critical invariant:

```text
hvac_action change
    !=
HVAC_MODE_CHANGE
```

Therefore:

```text
cooling -> idle -> cooling
```

while HVAC mode remains `cool` does not execute an Adaptive mode reset.

This prevents reintroducing the v0.1.2 Adaptive I reset bug.

# 29. Minimum required parity tests

## Direction and mode

- COOL uses `room - reference`
- non-COOL produces no balancing demand
- HEAT does not reverse the cooling formula
- HEAT_COOL produces no bedroom demand

## Base P rising thresholds

Test immediately below, exactly at, and immediately above:

```text
1.5
2.0
2.5
3.0
3.5
```

## Base P falling thresholds

Test immediately below, exactly at, and immediately above:

```text
1.3
1.8
2.3
2.8
3.3
```

## Hysteresis state

Examples:

```text
previous 4 / error 1.9 -> 4
previous 4 / error 1.8 -> 2
previous 8 / error 2.9 -> 8
previous 8 / error 2.8 -> 6
```

## Adaptive timing

- first observation initializes reference/time
- 19m59s does not evaluate
- 20m00s evaluates
- subsequent evaluation establishes a new observation window

## Adaptive poor improvement

```text
improvement < 0.2 -> +1
```

## Adaptive moderate improvement

```text
0.2 <= improvement < 0.5 -> hold
```

## Adaptive good improvement

```text
improvement >= 0.5 -> -1
```

## Anti-windup

- Adaptive evaluation cannot exceed `10 - base`
- NORMAL_UPDATE may preserve stored Adaptive I above new headroom
- the final PI Target remains capped at 10 during that interval
- the next Adaptive event clamps stored Adaptive I to current headroom
- Base P 10 forces Adaptive I to zero when Adaptive I evaluates
- PI Target never exceeds 10

## Balance reset

```text
error <= 1.3
```

must clear Adaptive I and observation history.

## Near-threshold unwind

```text
1.3 < error < 1.5
```

holds before evaluation is due and unwinds one step when due.

## Issue-regression test

The following sequence must preserve the same observation window:

```text
mode = cool
action = cooling

then

mode = cool
action = idle

then

mode = cool
action = cooling
```

No Adaptive I reset is allowed.

## True mode-change test

```text
cool -> off
off  -> cool
```

must be represented as true mode changes and start a fresh COOL adaptive cycle.

## Active-cooling minimum

```text
mode cool + action cooling + PI 0 -> effective Speed 1
```

## Idle balancing

```text
mode cool + action idle + PI 6 -> effective Speed 6
```

## Unsupported mode safety

```text
mode != cool -> effective Speed 0
```

## Invalid input safety

- missing reference temperature
- missing zone temperature
- non-numeric temperature

must result in safe zero PI/effective demand immediately.

Stored Adaptive state may remain preserved during `NORMAL_UPDATE` until the
next Adaptive event, but it must not produce a positive actuator command.

## Multiple-zone independence

Changing one zone's state must not mutate another zone's Adaptive I state.

## Central assist

```text
max PI < 8 -> false
max PI = 8 -> true
max PI > 8 -> true
mode != cool -> false
```

# 30. Phase 2 acceptance gate

The pure Python controller is not considered complete merely because it
produces plausible outputs.

Before connecting it to the Virtual HVAC Test Bench:

- all parity tests above must pass;
- controller code must contain no Home Assistant service calls;
- no room names may be hard-coded in controller logic;
- cooling-only behavior must match v0.1.3;
- Base P hysteresis must match v0.1.3;
- Adaptive I timing must match v0.1.3;
- the v0.1.3 attribute-only reset fix must have an explicit regression test;
- PI Target and effective target behavior must match v0.1.3;
- central-assist decision threshold must remain Speed 8.

Only after this gate passes should Home Assistant entity plumbing be attached to
the pure controller.

---

# 31. Deferred enhancements

The following must NOT be introduced during parity implementation:

- heating balancing;
- different Base P thresholds;
- different hysteresis;
- shorter or longer Adaptive I interval;
- different improvement thresholds;
- different anti-windup behavior;
- predictive control;
- occupancy control;
- weather compensation;
- self-tuning;
- cross-zone coupling;
- new central blower strategy.

These may be evaluated after v0.1.3 parity has been demonstrated.

---

# 32. Migration invariant

The Phase 2 migration contract is:

```text
Same inputs
+
same previous state
+
same event semantics
+
same elapsed time
=
same control decision
```

Any intentional difference must be documented as an enhancement after parity,
not silently introduced during the Python migration.
