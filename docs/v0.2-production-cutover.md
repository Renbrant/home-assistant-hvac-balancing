# v0.2 Production Cutover

## Purpose

This document defines the production migration from the legacy v0.1.3
YAML/Jinja HVAC balancing controller to the v0.2 Python Home Assistant
Custom Integration.

The migration has two primary goals:

1. safely transfer physical HVAC balancing authority to the Python controller;
2. preserve the existing Home Assistant entity IDs and Recorder history
   wherever a v0.1.3 calculated entity has a direct v0.2 equivalent.

The fundamental safety rule is:

> There must never be two physical HVAC balancing actuator authorities at the same time.

---

## Final migration strategy

The project performed a controlled direct cutover from v0.1.3 to v0.2.0-beta.9.

An additional long-running production shadow period is not required before
activation because the Python implementation has already been exercised through:

- Virtual HVAC Test Bench scenarios;
- Base P tests;
- hysteresis tests;
- Adaptive I / PI-lite tests;
- cooling-exposure tests;
- multi-zone tests;
- invalid/unavailable input tests;
- actuator tests;
- Central Assist tests;
- startup/reload/unload safety tests.

Production field monitoring is now the active validation stage.

```text
BEFORE CUTOVER

v0.1.3 YAML
    calculations: ON
    physical actuation: ON

v0.2 Python
    physical actuation: OFF


        CONTROLLED CUTOVER


AFTER CUTOVER

v0.1.3
    physical actuation: OFF
    retained temporarily for rollback/reference

v0.2 Python
    calculations: ON
    physical actuation: ON
    sole physical actuator authority
```

---

## Single physical authority

The legacy automation:

```text
HVAC - Smart Bedroom Booster Control
```

must be disabled before the Python controller assumes physical control.

The following condition is prohibited:

```text
v0.1.3 physical actuation ON
+
v0.2 physical actuation ON
```

The legacy and Python controllers must never command the physical booster fans
or Central Assist simultaneously.

# Historical entity compatibility

Historical entity compatibility is part of the v0.2 production migration
contract.

Where a v0.1.3 calculated entity has a direct v0.2 equivalent, the existing
Home Assistant `entity_id` should be preserved.

The purpose is to maintain continuity for:

- Home Assistant Recorder history;
- historical graphs;
- dashboards;
- automation references;
- analysis tools;
- field-history comparisons;
- statistics where applicable.

The controller implementation changes from YAML/Jinja to Python, but the public
Home Assistant entity interface should remain compatible wherever practical.

# Recorder preservation policy

The production migration must not purge historical HVAC balancing data.

Specifically:

- do not call `recorder.purge_entities` for the legacy HVAC entities;
- do not intentionally delete Recorder history;
- avoid simultaneous old/new ownership of the same `entity_id`;
- preserve the historical series wherever a Python entity directly replaces
  a v0.1.3 calculated entity;
- create a Home Assistant backup before the production cutover.

# Cutover Phase 1 - Disable legacy physical authority

Disable:

```text

```

Do not delete the automation during initial production validation.

It remains available as the immediate rollback path.

---

# Cutover Phase 2 - Release legacy calculated entity IDs

The legacy template entities that will be replaced by native Python entities
must not remain active simultaneously with the new entities under the same
Home Assistant IDs.

The transition should be:

```text
Legacy template entity stops
        |
        v
Legacy entity_id becomes available
        |
        v
Python entity assumes the equivalent entity_id
        |
        v
Recorder continues using the historical logical identity
```

Recorder data must not be purged.

# Initial validation criteria

The first production cooling cycles should confirm:

- Python is the only controller issuing physical commands;
- all three zones respond independently;
- minimum Speed 1 behavior works while actively cooling;
- boosters remain off outside supported COOL operation;
- proportional thresholds behave correctly;
- hysteresis prevents unnecessary oscillation;
- Adaptive I state evolves correctly;
- normal compressor `cooling -> idle -> cooling` cycling does not incorrectly
  reset the adaptive controller;
- Central Assist activates only when required;
- Central Assist release behaves deterministically;
- unavailable sensors fail safely;
- integration reload/unload fails safely;
- historical dashboards continue using the preserved entity IDs;
- Recorder history remains available across the migration boundary.

---

# Rollback

If unacceptable behavior is observed:

```text
1. Disable or unload v0.2 physical control.

2. Confirm Python is no longer issuing actuator commands.

3. Re-enable:
   HVAC - Smart Bedroom Booster Control

4. Confirm v0.1.3 has resumed physical authority.

5. Investigate the v0.2 behavior before another cutover.
```

Never enable v0.1.3 physical actuation while v0.2 is still actively controlling
the equipment.

---

# Legacy retirement

The v0.1.3 implementation should not be deleted immediately after the first
successful production cycle.

After sufficient real-world validation:

1. confirm historical entity continuity;
2. confirm dashboards and analysis tools work;
3. confirm multiple representative cooling cycles;
4. confirm Adaptive I behavior;
5. confirm Central Assist behavior;
6. confirm restart/reload behavior;
7. confirm fail-safe behavior;
8. confirm rollback is no longer operationally necessary.

Only then should obsolete v0.1.3 production configuration be removed.
